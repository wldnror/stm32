Firmware-stage power-on image (Pi Zero W / SH1107), version 3.79

Status: the user confirmed POWER ON is visible about one second after power
application on 2026-10-20. Firmware output is intentionally static and now omits
a frozen percentage bar. Native early animation bridges to Linux/app progress;
see native/README.txt. The prior cut-down/v1 setup was not physically successful.

This adds a static GDSENG / POWER ON image before Linux starts.
The native Linux helper later replaces it with animation, then the normal menu.
Only OLED address 0x3c on SDA2/SCL3 at 100 kHz is written. There are no delays,
loops, network operations or STM32 GPIO writes in the splash program.

Build the 1328-byte image without third-party Python dependencies:
  python3 firmware_splash.py deploy/stm32_power_on.bin --source deploy/stm32_power_on.splash

The binary uses version 2 and explicitly selects controller BSC1 (port byte 1).
The reference .splash file describes that intent. Upstream splash_assembler.py
at b57c48e97f7f43d95d86334798650cfda1ebc8a1 rewrites [port 1] to wire port 0.
Its output produced "Failed to display splash screen image" on this Pi; the
otherwise identical binary with wire port 1 completed the OLED transfer.
Use firmware_splash.py to build this asset, not that unmodified assembler.

Safe deployment:
1. Back up config.txt and cmdline.txt, and any boot files that will be replaced.
2. Install the matched standard pair under the custom filenames above; verify
   both hashes before selecting either file in a config.
3. Install the verified splash image. Build tryboot.txt from the saved original
   config plus the firmware section. Keep normal config as a known-working
   fallback; sync and reboot '0 tryboot' for a one-shot trial.
4. Check firmware version, transfer logs, menu READY, Wi-Fi and restart count.
5. After those checks pass, copy tryboot.txt atomically to config.txt and sync.
   A physical power cycle is still necessary to verify the first visible image.
6. deploy/stm32-headless.conf blocks unused video-driver autoloading.

Native animation and panel setup (3.79):
The installed native helper starts before systemd using a separate kernel
command-line copy selected by cmdline=gds-native-cmdline.txt. The original
cmdline.txt is retained. Native animation uses the same display lock/state and
hands over only when the application requests it. A thin moving bar segment,
activity dots and elapsed seconds keep motion visible between real stage
updates; the solid fill is tied to those stages. The wrapper falls back to the
Python renderer when the optional native binary is absent.
See native/README.txt for building, kernel-matched module preparation and trials.

Wi-Fi setup now clears preparation progress after AP/HTTP become ready, showing
SSID/password/address. A held SET press stays consumed through UI transitions,
duplicate setup requests are rejected and cancellation removes queued requests.
AP commands observe cancellation and a 45-second preparation deadline. Restoring
the last connection also stops an activation left running inside NetworkManager.
During setup, panel button events cannot act on the hidden underlying menu.
